# Monument QA Technical Challenge

Playwright + TypeScript test automation project created for the Monument Software QA Technical Challenge.

## Objective

Validate that Unit permissions correctly protect access to the Units area, including:

- Read access
- Create, edit, and delete permissions
- Direct URL protection
- Facility-level visibility
- Session and logout behavior
- Role-based access control

## Test strategy

The test suite prioritizes high-value scenarios that are safe, repeatable, and suitable for the challenge timeframe.

The current automation covers:

- Admin authentication
- Access to Individual Units and Unit Groups
- Opening existing Units and Unit Groups
- Direct authenticated access to protected Unit routes
- Access to Add Unit and Add Unit Group forms
- Logout and protection of direct Unit URLs after logout

Additional permission-focused coverage is planned using dedicated test users:

- A user without Unit View permission
- A view-only user without Create, Edit, or Delete permissions

These users are created manually as test data setup so the automation can focus on validating permission enforcement rather than mailbox activation, password setup, and user provisioning.

## Main design decisions

### Page Object Model

Page-specific locators and interactions are kept inside page objects.

- `LoginPage` handles authentication and logout.
- `UnitsPage` handles Unit navigation, Unit Groups, direct URLs, and Unit forms.

This keeps tests focused on behavior and expected results instead of implementation details.

### Explicit authentication

Each test performs its own login to remain self-contained and easy to understand.

For a larger test suite, authenticated `storageState` files or custom fixtures could be introduced for each role, such as admin, view-only, and no-view users.

### Stable locators

The project prioritizes:

1. Accessible roles and names
2. `data-testid`
3. Stable route patterns

Dynamic CSS classes generated by Material UI are intentionally avoided.

### Parallel execution

The suite supports parallel execution because each test uses an isolated browser context and does not currently depend on another test.

Worker count should still be adjusted according to:

- Staging environment capacity
- Session limitations
- Test-data collisions
- CI runner resources

Any future create, update, or delete tests should use unique data and reliable cleanup before being enabled in parallel.

### Test artifacts

The Playwright configuration retains useful debugging evidence:

- HTML report
- Screenshot on failure
- Trace on retry
- Video on failure, when enabled

## Automated versus manual coverage

### Automated

The automated suite focuses on repeatable permission and access checks that do not require complex external setup.

Examples:

- Authorized navigation
- Protected route access
- Unit and Unit Group page access
- Form availability
- Logout protection

### Manual or test-data setup

The following scenarios may require manual preparation or controlled test data:

- Creating and activating invited users
- Creating and assigning restricted roles
- Mailbox activation
- Permission changes during an active session
- Facility isolation across known test records
- Client-side manipulation and request tampering
- Session expiry behavior
- Cleanup of complex Unit Group pricing data

These scenarios remain part of the written test design even when they are not automated within the challenge timeframe.

## Planned high-value improvements

The next automation priorities are:

1. Verify that a user without Unit View cannot see Units in navigation.
2. Verify that direct Unit and Unit Group URLs are blocked without Unit View.
3. Verify that a view-only user can read Units but cannot create, edit, or delete.
4. Add a controlled Unit create, update, and delete lifecycle with unique data and cleanup.
5. Validate facility-level isolation using a user restricted to one facility.

## Notes for reviewers

This framework was intentionally kept lightweight.

The goal was to demonstrate:

- Risk-based test selection
- Clear test design
- Maintainable Playwright structure
- Stable locator strategy
- Environment-based configuration
- CI execution
- Practical trade-offs between coverage, setup cost, and challenge time

More complex fixtures, API-based data setup, role-specific storage states, broader browser coverage, and advanced reporting would be introduced as the test suite grows.
